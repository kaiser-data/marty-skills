# Variance First

## Overview

A design written while looking at one example absorbs that example. The result runs
perfectly on the sample it was built from and produces wrong — often plausible — output on
the second source.

**Core principle: never design against one source. What varies across sources has to be
observed before it can be handled, and observation needs more than one sample.**

The output is not code. It is a **variance table** plus a one-line input contract, written
before planning starts, which the sibling skill agnostic-audit later checks the built code
against.

## The gate

**Three real samples, from three different origins, before design starts.**

Different *origin*, not different file:

- Three rows of one CSV is one source
- Three exports from the same tool is one source
- Three pages from one site, generated by one template, is one source
- Three files from three producers is three sources

Origin means a different producer. If the same code emitted every sample, what has been
seen is one implementation's habits, not the format.

## Getting the samples

In order of trustworthiness, best first:

1. **A format spec** — RFC, JSON Schema, OpenAPI, vendor documentation, a standard. A spec
   states what is *guaranteed*, which samples can only hint at. One real spec is worth more
   than ten samples, because it distinguishes coincidence from contract.
2. **Real public datasets** — already produced by many hands
3. **Freshly collected real sources** — scrape, export, or request more
4. **Vendor sandbox output** — real code path, unrepresentative content

**Synthetic samples never count toward the three.** They are generated from the
assumptions already held, so they confirm rather than test, and they invent structure no
real producer emits — the failure runs in exactly the direction that defeats the exercise.
Synthetic material is allowed only to probe an edge case already *observed* in a real
sample, and must be labelled as synthetic wherever it is stored.

If three origins genuinely cannot be obtained, that is a finding, not a formality to skip.
Write it down as a stated risk in the design, name what remains unobserved, and treat every
untested field as Unknown below.

## The diff step

Put the samples side by side and sort every field, structure, and encoding decision into
one of three columns:

| Column | Meaning | What the code must do |
|---|---|---|
| **Invariant** | True in all samples **and there is a stated reason why** — a spec, standard, or guarantee | Safe to assume |
| **Varies** | Differs across samples | Derive it at runtime, or declare it per source in config |
| **Unknown** | Only one sample shows it; no stated guarantee | Assert it — check and fail loud |

The load-bearing rule: **agreement across samples is not invariance.** Three samples
agreeing may only mean they were sourced badly. Invariance requires a *reason* that can be
named. Without one, the row belongs in Unknown.

Unknown is the column that catches the real failure mode, which is why **a variance table
with an empty Unknown column has not been filled in honestly.** Three samples cannot
possibly settle every question; an empty Unknown means the questions were not asked.

## Prompt discipline

If any part of this consumes the source through a prompt, the prompt is code and gets the
same treatment. Write it against the table, never against the sample:

- **No proper nouns lifted from samples** unless genuinely part of the contract. Company
  names, people, product names, and dates from the example silently narrow the task.
- **Few-shot examples from at least two origins.** With one origin, the model learns that
  origin's style *as the task* and quietly rejects everything else.
- **Every structural claim traces to an Invariant row.** "The title is on the first line"
  is either in Invariant with a reason, or it is not in the prompt.
- **A claim tracing to Unknown becomes a runtime check**, not an instruction.
- **Output schemas describe the domain**, not one document's layout.

## The artifact

Two things, pasted into the spec or plan before task decomposition:

1. The **variance table** — all three columns, Unknown non-empty
2. A **one-line input contract** — what this accepts, stated as a claim someone could
   disprove with a counterexample

Name the three origins alongside it. An artifact that does not say where its samples came
from cannot be checked later.

## Handing off

The variance table is the input that makes agnostic-audit checkable: Varies rows must
appear in the code as Derived or Declared, Unknown rows as Asserted. An audit run without a
variance table has to reconstruct the contract by guesswork.

If the audit later finds a Critical coupling, come back here and reopen the table rather
than patching the line — a silent coupling usually means a row was misfiled as Invariant.

## Common mistakes

| Mistake | Why it bites |
|---|---|
| Counting files instead of origins | Three exports from one tool is one source |
| Filing agreement as Invariant | The reason is what makes it invariant, not the tally |
| Leaving Unknown empty | Means the hard questions were skipped, not answered |
| Generating samples to reach three | They carry the same assumptions, so they cannot test them |
| Gating the code but not the prompt | The prompt is where one example's content hides |
| Writing the contract from imagination | A contract with no observations behind it is a guess with formatting |
| Deferring the gate to "after the prototype" | The prototype becomes the design |

## Red flags — treat the gate as unmet

- "The format is standard" — name the spec, or it is an assumption
- "All three samples look the same" — same producer?
- "It will be generalised once a second source shows up" — the first design decides the shape
- "A few variants were generated to be safe" — from what knowledge?
- "This one is representative" — of what population, observed how?
- "It is only for this client" — undated, and the second client always arrives
