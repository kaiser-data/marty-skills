> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship two sibling skills — `variance-first` (pre-build gate that forbids designing against one example source) and `agnostic-audit` (post-build audit that inventories every place code is welded to the source it was built from).

**Architecture:** Both are pure prose skills in `skills/public/`, holding to the audit anatomy `mock-purge` established: classification table → required inventory with named fields → one load-bearing field that forces the concrete case → mandatory verdict → common mistakes → red flags. No scripts in v1. Each skill's `evals/evals.json` is written **before** its SKILL.md and acts as the trigger contract the description must satisfy.

**Tech Stack:** Markdown + YAML frontmatter (Agent Skills portable core), JSON evals, `skills/public/skill-forge/scripts/forge.py` (stdlib Python 3) for validation and dashboard.

## Global Constraints

- Both skills go in `skills/public/` — they contain no hostname, IP, username, or path from the local setup, so the private repo rule does not apply.
- Frontmatter uses the **portable core only**: `name`, `description`. No `when_to_use`, no `allowed-tools`, no Claude Code extensions — `forge.py validate` warns on non-portable fields.
- `name` must match the directory name exactly, kebab-case.
- `description` must be 1–1024 chars, contain **no `<` or `>` characters**, be written in third person (not "I"), and contain an explicit "Use when" trigger clause.
- **Refer to a sibling skill by bare name only** (`variance-first`, `mock-purge`) — never as a path like `skills/public/variance-first/SKILL.md`. Path-shaped references to other skills trip the validator's broken-file-reference warning.
- SKILL.md bodies stay under 500 lines and 5,000 words.
- No `TODO`, `TBD`, `FIXME`, or `XXX` markers in shipped skill files — the validator flags them as leftover placeholders.
- Acceptance bar for every task that touches a skill: `forge.py validate` reports **0 errors, 0 warnings**.
- Commits happen only when the user has explicitly said to commit (repo rule). Treat each `git commit` step as "stage and propose, commit on go".

# Agnostic Audit

## Overview

An implementation welded to the one source it was developed against runs perfectly and is
still broken. Nothing here is simulated — the code genuinely works. It only works once.

**Core principle: every assumption about the input must be derived, declared, or asserted.
An assumption that is merely held is a defect, and one that fails silently is critical.**

This is the sibling of mock-purge, on a different axis. That audit asks whether behaviour
is real. This one asks whether real behaviour generalises. A codebase can pass one and
fail the other.

Being source-agnostic is a production requirement, not a matter of style.

## The distinction that decides everything

Classify every finding by **coupling class**, not by how ugly the line looks:

| Class | Example | Verdict |
|---|---|---|
| **Derived** — read from the input at runtime | finds the column by matching its header | Fine |
| **Declared** — source specifics live in config, args, or an adapter | per-source field map in configuration | Fine |
| **Asserted** — assumption is baked in but checked; violation fails loud and names itself | requires an `id` key, raises saying which key is missing | Acceptable |
| **Assumed, loud** — unchecked, but a different source crashes it | `row[3]` on a shorter row, raising IndexError | Defect — honest, still broken |
| **Assumed, silent** — unchecked, and a different source yields *plausible wrong output* | `row[3]` returning some other column's value | **Critical** |

The bottom row is the same critical case as a silent mock: output that looks right and is
not. Everything above it is triage.

**Severity rises with the cost of being wrong.** Where the output's only value is its
correctness — facts, money, safety, medical, legal, compliance — a silent coupling is
critical no matter how narrow the input variance appears, because the product's single
promise is that the answer can be trusted.

## Sweep surfaces

Four surfaces. An audit that covers fewer must say which it skipped.

**1. Data and format.** Literals lifted from the sample (column headers, JSON keys, IDs,
names, dates, URLs, magic strings), positional indexing (`[0]`, `[3]`, last element),
regexes tuned to one sample's whitespace or casing, assumed key presence, assumed key or
row ordering, assumed encoding, delimiter, quoting, line ending, locale, timezone, date
format, decimal separator, currency, unit.

**2. Environment and machine.** Absolute paths, home directories, usernames, hostnames,
private network names, assumed installed binaries, assumed ports, assumed shell, path
separators, case-sensitive filesystem assumptions.

**3. Repo and project shape.** Assumed directory names, package manager, lockfile, branch
name, monorepo layout, or that a given config file exists at all.

**4. Prompt and spec.** Instructions naming entities drawn from the sample, few-shot
examples all from one origin, output schemas shaped around one document's layout,
structural assertions like "the title is on the first line", vocabulary that belongs to one
domain rather than the task.

Surface 4 is read, not grepped, and is the one most often skipped. It is also the most
damaging, because the artifact holding the assumption is prose — no linter, type checker,
or test will ever see it. A prompt that was written while looking at one example has
absorbed that example whether or not it quotes it.

```bash
# Starting sweep for surfaces 1-3. Adjust the exclude list to the repo.
# Surface 4 is not greppable - read every prompt and instruction file by hand.
grep -rnE '/Users/|/home/|localhost|127\.0\.0\.1|\[[0-9]+\]|\.iloc\[|utf-8|latin-1' . \
  --exclude-dir={.git,node_modules,vendor,dist,build,target,.venv,__pycache__}
```

Then, per hit, the question that decides its class: **where does this value come from when
the input is a different one?** Trace it from the input and from configuration, not from
the line it sits on.

## Required inventory

Report every finding with all five fields. A finding missing a field is not yet audited.

| Field | Why it is required |
|---|---|
| **Location** | file:line, so it can be acted on |
| **Assumes** | the assumption written as a claim about the source |
| **Class** | from the coupling table above |
| **Breaks when** | a **concrete second source** that violates it |
| **Action** | derive, declare, assert, or keep with a stated reason |

**Breaks when** is the field that changes decisions. "A CSV with columns in a different
order" is a note. "The vendor's export, which puts `email` last and quotes every field" is
a finding. If no real second source can be named, the finding is not audited yet — being
unable to name one almost always means the assumption is not yet understood.

## The N=1 test

> Has this produced correct output from a source it was **not** built from? Name it.

If every run and every fixture used the origin sample, that fact is reported next to any
pass count. "All tests pass" and "every fixture is the sample the code was written from"
are both true, and must appear together.

Adding more files from the same producer does not answer this test. Three exports from one
tool are one source.

## Verdict

State one of these, never a bare "looks generic":

- **Source-agnostic** — every coupling is Derived or Declared. Name the second source it
  was verified against, and say which surfaces were swept.
- **Coupled but honest** — remaining assumptions are Asserted and fail loud. List them.
- **Silently coupled** — list findings, each with its breaks-when sentence.

## Feeding back into the design

Findings are not patched in isolation. Any **Critical** whose fix changes what the code
assumes about its input **reopens the variance table** — see the sibling skill
variance-first — instead of being fixed at the line.

A silent coupling is usually evidence that the input contract was never established.
Repairing the line while leaving the contract unwritten reproduces the same bug in the next
feature that touches the same source.

## Common mistakes

| Mistake | Why it bites |
|---|---|
| Auditing code but not prompts | Surface 4 is where the sample's content hides; nothing will flag it for you |
| Reporting a count | Six Declared couplings are fine. One silent one is not. Class beats count. |
| "It is a standard format" | Whose standard? Name the spec, or it is an assumption |
| Testing against more copies of the same source | Still N=1; the second source needs a different producer |
| Fixing the line, not the contract | The same assumption returns in the next feature |
| Treating agreement as guarantee | Samples agreeing may only mean they were sourced badly |
| Auditing by directory | Couplings live in ordinary source files, config defaults, CI env, and IaC |

## Red flags — treat as unaudited

- "It is a generic parser" — verified against what?
- "The other sources will look the same" — that is the assumption under audit
- "I generated test data covering the variants" — generated from your own assumptions
- "It only needs to work for this one source" — undated, and the second source always arrives
- "The tests pass" — against the sample they were written from?
- "I will make it configurable later" — the silent version ships in the meantime

# Variance First

## Overview

A design written while looking at one example absorbs that example. The result runs
perfectly on the sample it was built from and produces wrong — often plausible — output on
the second source.

**Core principle: you may not design against one source. What varies across sources has to
be observed before it can be handled, and observation needs more than one sample.**

The output is not code. It is a **variance table** plus a one-line input contract, written
before planning starts, which the sibling skill agnostic-audit later checks the built code
against.

## The gate

**Three real samples, from three different origins, before design starts.**

Different *origin*, not different file:

- Three rows of one CSV is one source
- Three exports from the same tool is one source
- Three pages from one site, generated by one template, is one source
- Three files from three producers is three sources

Origin means a different producer. If the same code emitted all your samples, you have
seen one implementation's habits, not the format.

## Getting the samples

In order of trustworthiness, best first:

1. **A format spec** — RFC, JSON Schema, OpenAPI, vendor documentation, a standard. A spec
   states what is *guaranteed*, which samples can only hint at. One real spec is worth more
   than ten samples, because it distinguishes coincidence from contract.
2. **Real public datasets** — already produced by many hands
3. **Freshly collected real sources** — scrape, export, or request more
4. **Vendor sandbox output** — real code path, unrepresentative content

**Synthetic samples never count toward the three.** They are generated from the
assumptions you already hold, so they confirm rather than test, and they invent structure
no real producer emits — the failure runs in exactly the direction that defeats the
exercise. Synthetic material is allowed only to probe an edge case already *observed* in a
real sample, and must be labelled as synthetic wherever it is stored.

If three origins genuinely cannot be obtained, that is a finding, not a formality to skip.
Write it down as a stated risk in the design, name what remains unobserved, and treat every
untested field as Unknown below.

## The diff step

Put the samples side by side and sort every field, structure, and encoding decision into
one of three columns:

| Column | Meaning | What the code must do |
|---|---|---|
| **Invariant** | True in all samples **and you can say why** — a spec, standard, or stated guarantee | Safe to assume |
| **Varies** | Differs across samples | Derive it at runtime, or declare it per source in config |
| **Unknown** | Only one sample shows it; no stated guarantee | Assert it — check and fail loud |

The load-bearing rule: **agreement across samples is not invariance.** Three samples
agreeing may only mean they were sourced badly. Invariance requires a *reason* you can
name. Without one, the row belongs in Unknown.

Unknown is the column that catches the real failure mode, which is why **a variance table
with an empty Unknown column has not been filled in honestly.** Three samples cannot
possibly settle every question; an empty Unknown means the questions were not asked.

## Prompt discipline

If any part of this consumes the source through a prompt, the prompt is code and gets the
same treatment. Write it against the table, never against the sample:

- **No proper nouns lifted from samples** unless genuinely part of the contract. Company
  names, people, product names, and dates from the example silently narrow the task.
- **Few-shot examples from at least two origins.** With one origin, the model learns that
  origin's style *as the task* and quietly rejects everything else.
- **Every structural claim traces to an Invariant row.** "The title is on the first line"
  is either in Invariant with a reason, or it is not in the prompt.
- **A claim tracing to Unknown becomes a runtime check**, not an instruction.
- **Output schemas describe the domain**, not one document's layout.

## The artifact

Two things, pasted into the spec or plan before task decomposition:

1. The **variance table** — all three columns, Unknown non-empty
2. A **one-line input contract** — what this accepts, stated as a claim someone could
   disprove with a counterexample

Name the three origins alongside it. An artifact that does not say where its samples came
from cannot be checked later.

## Handing off

The variance table is the input that makes agnostic-audit checkable: Varies rows must
appear in the code as Derived or Declared, Unknown rows as Asserted. An audit run without a
variance table has to reconstruct the contract by guesswork.

If the audit later finds a Critical coupling, come back here and reopen the table rather
than patching the line — a silent coupling usually means a row was misfiled as Invariant.

## Common mistakes

| Mistake | Why it bites |
|---|---|
| Counting files instead of origins | Three exports from one tool is one source |
| Filing agreement as Invariant | The reason is what makes it invariant, not the tally |
| Leaving Unknown empty | Means the hard questions were skipped, not answered |
| Generating samples to reach three | They carry your assumptions, so they cannot test them |
| Gating the code but not the prompt | The prompt is where one example's content hides |
| Writing the contract from imagination | A contract with no observations behind it is a guess with formatting |
| Deferring the gate to "after the prototype" | The prototype becomes the design |

## Red flags — treat the gate as unmet

- "The format is standard" — name the spec, or it is an assumption
- "All three samples look the same" — same producer?
- "I will generalise it once a second source shows up" — the first design decides the shape
- "I generated a few variants to be safe" — from what knowledge?
- "This one is representative" — of what population, observed how?
- "It is only for this client" — undated, and the second client always arrives
